## Findings

### F1 — [fix-now, confirmed by direct behavior check] Amending an already-applied Alembic migration silently desyncs any pre-existing database

**Source:** PR #8 body ("Amended migration 0006 in place (unreleased within this epic)") + direct reproduction against the local `sinaliza-dev-postgres` container during this retro.

Story 2.2 (PR #8) discovered `SyntheticProfile` needed a 4th member (`FALLING_GRADES`) and fixed it by **editing migration `0006` in place** rather than adding a new migration, reasoning that 0006 was "unreleased" within the epic. That reasoning holds for a database that had never run 0006 before the edit — but this session's local dev database *had*: it ran 0006 (with only 3 enum members) during Story 2.1's work, before 2.2's amendment landed.

Reproduced live: `alembic current` / `alembic heads` both reported `0006 (head)` — Alembic considers the database fully migrated — yet:

```sql
SELECT enumlabel FROM pg_enum WHERE enumtypid = 'synthetic_profile'::regtype ORDER BY enumsortorder;
-- STABLE, FALLING_ATTENDANCE, COMBINED_DETERIORATION   (FALLING_GRADES missing)
```

Running `python -m app.synthetic.generate --seed 123 --reset` against this database failed with `psycopg.errors.InvalidTextRepresentation: invalid input value for enum synthetic_profile: "FALLING_GRADES"` — a real crash, not a theoretical risk. Alembic gives no signal that anything is wrong: it has no mechanism to detect that an already-applied revision's *content* changed after the fact.

This is invisible to every story's own test suite, because `backend/tests` builds its schema fresh (effectively `create_all` from the current models/migration state) for every test run — it always sees the migration file's current content, never a database that ran an older version of the same revision. It only surfaces on a database that existed *before* the amendment: a teammate's local dev DB, a long-lived staging DB, or (relevant to Epic 6) any environment provisioned mid-epic rather than from a fresh image.

**Disposition:** fix-now. **Process lesson:** never amend an already-applied Alembic migration in place. "Unreleased" must be judged against every environment that might already be running it (including every developer's local dev DB), not against elapsed time within the current epic — add a new migration instead, even for a same-epic fix.

### F2 — [defer, low] `GENERATOR_VERSION` does not track every story that changed generator output

**Source:** `backend/app/synthetic/generate.py` history across the range — confirmed `GENERATOR_VERSION = "2.2.0"` was still the value on `master` at commit `3330904` (after 2.2 and 2.4 had both already merged), then jumped to `"2.3.0"` (Story 2.3) and finally `"2.5.0"` (Story 2.5, the version that survived the merge).

The constant's own comment says it should be "bumped by any story that changes what the generator emits." Story 2.4 added `TRAIN_EVAL_SPLIT_RATIO` as a named, provenance-tracked constant but never bumped the version (the emitted value, 0.7, didn't change — only its documentation did), so this may be a defensible judgment call rather than an oversight. Not a functional defect: no generated content is wrong, only the provenance audit trail has a gap a future `SyntheticGenerationRun.generator_version` reader can't fully explain.

**Disposition:** defer. Low severity, cheap to fix whenever `generate.py` is next touched — no dedicated story needed.

### F5 — [accepted] Shared-file boundaries between concurrently-built stories reconciled correctly

4 of 5 stories touched `generate.py`; 3 touched `fingerprint.py`; 2.3 and 2.5 ran in parallel worktrees against the same pre-2.3/2.5 base and both modified `generate.py`. Checked for the two most likely integration failures:

**Disposition:** accepted — no integration defect found at the 2.3/2.5 boundary or across the wider 5-story surface.
