- (decision) Paradigma: Arquitetura em camadas (Domain/Application/Infrastructure/Presentation) com regra de dependência explícita (domain sem imports de framework; application só via ports; infrastructure implementa ports; presentation só chama application; ml só lê domain/ports) + Pipeline pattern nos dois pontos que precisam de sequência idêntica em todo ponto de uso (detecção de sinais; pré-processamento+modelo de ML) — alinhado a AGENTS.md ("request → validation → application service → domain/repository → response", "pipeline único do Scikit-Learn", RNF-09 camadas)
- (decision) AD-1: TrajectorySnapshot/TrajectoryChange nunca são recomputados por job agendado; são calculados dentro da própria requisição HTTP que precisa deles (GET home, GET trajetória do aluno) e a mesma requisição faz upsert idempotente das linhas resultantes — dá estabilidade de FK para FollowUpEvidence.trajectory_change_id sem violar "sob demanda, nunca agendado". Resolve tensão entre RF-11 (mudança precisa apontar para registro persistente e estável) e a restrição de nunca rodar em job agendado. Home precisa agregar ~200 alunos por requisição — decisão: preferir consulta set-based (SQL/agregação), não loop-por-aluno em Python, para caber no orçamento RNF-01 (5s); só otimizar com cache se medição real mostrar risco (ver Deferred).
- (decision) AD-2: regra de dependência em camadas (ver Paradigma) — nomeia o paradigma e o diagrama de dependência; nunca hexagonal formal com múltiplos adapters (autor único, YAGNI), mas ports/interfaces de repositório mínimos o suficiente para o `ml/` e os testes não dependerem de infraestrutura concreta
- (decision) AD-3: treino/avaliação de ML é processo offline via CLI manual (nunca disparado pelo app rodando, nunca agendado); inferência ao vivo (se/quando a tela técnica de score existir) carrega o artefato serializado uma vez por processo (singleton no startup/cache em memória), nunca recarrega nem retreina por requisição — já alinhado a AGENTS.md ("não carregar artefato ML a cada request"). Score/ranking de ML nunca aparece em endpoint/schema de resposta do produto (`/students`, `/follow-ups`); vive atrás de um boundary interno separado (`/research/*` ou notebook), nunca junto ao contrato de API do produto.
- (decision) AD-4/AD-5: dois recortes via `Student.dataset_split` (TRAIN/EVAL_DEMO), decidido na geração sintética (não em query time), na mesma base Postgres (nunca 3 bases); truncagem "hoje" centralizada num único utilitário `as_of()` no domain, nunca `date.today()` disperso nem um terceiro dataset nem mutação de linha persistida — evita dois módulos (serviço de trajetória vs. script de avaliação de ML) truncando o "hoje" de forma inconsistente
- (decision) AD-6: status de FollowUp é ENUM nativo do Postgres com os 4 valores fechados (nunca coluna de texto livre, para impedir um 5º estado tipo "HIGH_RISK" entrar mesmo via patch direto no banco) e só muda pelos 4 estados fechados via método de application service (nunca atribuição direta de campo); toda ação e mudança de status é append-only (nunca update/delete de ação anterior) — reforça RNF-11 e a proibição explícita de estado HIGH_RISK (AGENTS.md)
