## Fix-now verification (from user-reported prior findings, independently re-checked against current master)

1. **`Notas.tsx` stale row-state across disciplina/período/data change** — FIXED, verified correct. `frontend/src/pages/Lancamento/Notas.tsx:150-158` adds a second `useEffect` (deps `[selectedPeriodId, subject, date]`, deliberately excluding `token`/`selectedClassroomId`) that blanks every row's `value`/`message`/`isError` back to default whenever any of those 3 shared-context fields changes, without touching the network. The original roster-fetch effect (`Notas.tsx:115-148`) keeps its original `[token, selectedClassroomId]` deps, unchanged — so changing subject/período/data no longer re-fetches the roster over the network. Traced through the mount/selection/race sequence by hand: no double-reset, no lost-update race with the async roster fetch (the fetch's own `.then()` always writes the authoritative fresh `rowStates` last for a turma change; the second effect only fires on the other 3 fields, which don't overlap with a turma change in the same render). **Consistency with `Presenca.tsx`/`Atividades.tsx` — confirmed deliberate and defensible, not an inconsistency:** `Presenca.tsx`'s roster effect (`Presenca.tsx:79-112`) puts `date` directly in the fetch-effect's deps and lets the re-fetch's completion supply fresh `rowStates`; `Atividades.tsx`'s submission-roster effect (`Atividades.tsx:141-174`) does the same with `[token, selectedClassroomId, selectedAssignmentId, submissionDate]`. ### New — fix now

**FN-1. `Grade` accepts a whitespace-only `subject` where the two structurally-parallel endpoints reject it.** Verified directly: `backend/app/presentation/schemas/grades.py:26` — `subject: Annotated[str, Field(min_length=1, max_length=255)]`, no `strip_whitespace`. Compare `backend/app/presentation/schemas/assignments.py:19` (`AssignmentCreateRequest.subject`) and `backend/app/presentation/schemas/observations.py:22` (`PedagogicalObservationCreateRequest.text`), both `StringConstraints(strip_whitespace=True, min_length=1, ...)` — added specifically to reject whitespace-only input. Story 1.3 (grades) shipped before that convention existed and was never backported when Stories 1.4/1.5 established it. A direct API call bypassing the frontend's own `.trim()` can persist `Grade.subject = "   "`; the identical payload shape 422s on `/assignments` and `/pedagogical-observations`. *Fix:* add the same `StringConstraints` to `grades.py:26`.

**FN-2. Story 1.1's own frozen spec contract for a stale/invalid bearer token was never implemented by any of the 4 stories it governs.** Verified directly against `docs/spec-1-1-autenticacao-coordenacao-pedagogica.md:43` (I/O Matrix): `Stale/invalid bearer token | Future protected call carries expired/invalid JWT | get_current_user raises 401 with the same envelope shape | Frontend clears session, redirects to /login`. The backend half is done (`backend/app/presentation/auth/dependencies.py:36-50`). The frontend half is not implemented anywhere — independently confirmed by direct grep (`grep -rn "401" frontend/src` → zero status-401-specific branches): `frontend/src/api/client.ts`'s `request()` (line 76) turns every non-2xx response into a generically-handled `ApiError`; none of the 4 Lançamento pages' `catch` blocks inspect `.code`/`.status`; `AuthContext.logout()` (`AuthContext.tsx:69`) is wired only to `Header.tsx`'s manual "Sair" button; `ProtectedRoute` only checks whether a session object exists in `localStorage`, never the JWT's own expiry. Story 1.1 itself had no protected route to test this row against by design (its scope excludes protecting anything but issuing the token) — this row only becomes checkable once Stories 1.2–1.5 exist, which is exactly why no single story's own review caught it; it is a genuine epic-aggregate gap. **This upgrades the previously-deferred "centralize 401/session-expiry handling" item from *defer* to *fix-now*** — it is an unmet, already-approved spec-contract row, not merely a UX enhancement. *Impact today is recoverable, not data-corrupting*: writes still fail closed (401), the user can manually log out/in.
