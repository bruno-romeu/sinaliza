### Diff-scope review (bmad-review: adversarial, edge-case-hunter, verification-gap)

All three lenses run in parallel against the full epic diff (`303ff90^..f3789c3`), explicitly weighted toward cross-story boundaries. Convergent and unique findings, each re-verified against the primary source (and where practical, against the live running app — see Behavior verification):

1. **[Confirmed by all 3 lenses + live verification] Registering a `FollowUpAction` never refreshes the visible "Histórico de ações" on the same screen.** `frontend/src/pages/Acompanhamento.tsx`: `ActionForm` (lines 441-540) takes no callback prop and never triggers a refetch; `ActionHistory` (lines 123-164) renders only from the `detail.actions` snapshot loaded once on mount in `Acompanhamento` (line 196). Unlike `StatusSelector`, which is wired with `onStatusChange` (lines 322-326) to update parent state. A user submits an action, sees "Registro salvo.", but the action does not appear in the history until the page is reloaded. Neither Story 4.2's test (checks only the POST + success message) nor Story 4.3's test (checks only a static, server-returned `actions` array on initial load) exercises the combination — a genuine cross-story gap. **Disposition: fix now.**
2. **[Confirmed by adversarial + edge-case claim-check + live HTTP verification] RF-22's visibility scoping covers only the evidence-card read path, not the raw observation timeline on the same page.** `backend/app/application/trajectory/get_student_trajectory_detail.py:255-260` (`_recent_observations`) calls `PedagogicalObservationRepositoryPort.list_by_student_in_range` — the unfiltered read — and is never passed `requesting_user_id`, unlike `resolve_evidence` (line 151) which is. **Verified live** against the running app (dev DB, real HTTP calls, two real users): the identical `PedagogicalObservation` text ("Notas um pouco abaixo do padrão anterior neste período.") was returned **redacted** by `GET /follow-ups/{id}`'s evidence card for a non-responsible user, and returned **in full** by `GET /students/{id}/trajectory/detail`'s `observations` array for the *same* user in the *same* session. RF-22 is implemented as a cosmetic placeholder in one of two places the identical string renders, not as an effective access control. Story 4.4's own spec Design Notes left the raw timeline "unfiltered by design," but did not anticipate (or at least did not document) that the two surfaces co-render the identical underlying text. **Disposition: fix now** — this is the epic's one security-relevant finding.
3. **[Confirmed by adversarial + live HTTP verification] No authorization boundary on `FollowUp` mutation, inconsistent with Story 4.4's new read-side trust boundary.** Story 4.4 introduced a real scoping rule keyed on `responsible_user_id` for *reading* evidence text, but Stories 4.1/4.2's write endpoints (`PATCH /follow-ups/{id}/status`, `POST /follow-ups/{id}/actions`) apply the pre-existing "any authenticated user" model (AD-8, consistent with every other route in the codebase) with no additional scoping. **Verified live**: a non-responsible second user successfully changed a `FollowUp`'s status via `PATCH` (HTTP 200) on a case whose evidence text that same user was blocked from reading moments earlier. No story's own review caught this because each only looked at its own endpoints in isolation. This is not necessarily a bug — AD-8 deliberately keeps a single flat role for the whole system — but the asymmetry (can mutate a case, cannot read why it was opened) was never an explicit decision. **Disposition: open question for the human** (see below) — a fix here depends on a product decision Epic 4's stories never had.
4. **[verification-gap, narrow] TOCTOU race in the freeze-on-evidence guard.** `sqlalchemy_trajectory_change_repository.py`'s `upsert` freeze branch has a narrow window where a concurrent recompute landing between `OpenFollowUpService`'s read and the evidence insert could still delete+reinsert sources for a change about to be frozen. Low likelihood given the single-coordenação, single-role demo system this epic targets; no test demonstrates it is reachable today. **Disposition: accept as-is**, revisit only if Epic 6's hosting model introduces genuine concurrent multi-session use.
5. **[edge-case, trivial] `EvidenceCard` renders a bare empty list when an evidence group has zero items.** Currently unreachable — every `FollowUp` this epic's code can create has ≥1 evidence item (AD-7 guarantee) — same class already accepted-as-false in Stories 4.1/4.3's own triage logs. **Disposition: accept as-is.**
6. **[edge-case, trivial] `EstudanteTrajetoria.tsx`'s "Abrir acompanhamento" failure path shows a generic error instead of the specific backend message**, unlike `ActionForm`/`StatusSelector` which do surface it. Minor UX inconsistency, not a correctness bug. **Disposition: accept as-is** (optional future polish).
7. **[adversarial, already tracked] Home's new "Acompanhamentos em andamento" section has no own retry on `loadError`.** Already raised and explicitly rejected as low-priority in Story 4.5's own triage log (finding 6) — not a new finding. **Disposition: accept as-is** (already decided).
8. **[adversarial, already tracked] The `GRANT`/`REVOKE` append-only backstop on `follow_up_action` is enforcement-inert in dev/test** because the connected role is a Postgres superuser. Already recorded in `docs/deferred-work.md` (spec-4-2 entry) with the exact same evidence. **Disposition: no new action** — cite the existing entry.
9. **[adversarial, already tracked] No uniqueness guard against opening a duplicate `FollowUp` for the same `trajectory_change_id`.** Already explicitly triaged and rejected as low-risk in Story 4.1's own spec (finding 1: single-tab button-disable mitigation). Re-raised because Story 4.5 now lists follow-ups on Home, which would make a duplicate *visible* rather than just a wasted row — no new reachability demonstrated, but the user-facing cost of the same latent gap went up. **Disposition: accept as-is**, reconsider only if a duplicate is ever actually observed.
10. **[adversarial, doc drift] `docs/epic-4-context.md:45` contains a stale, never-implemented claim**: "`FollowUp.next_review_date` is read only by a live query inside `GET /home`." No story implements this — `next_review_date` stays `NULL`/unused end to end (confirmed: `list_active()` filters only on `status != ENCERRADO`), exactly as each story's own Boundaries correctly state. Only the rolled-up epic-context doc is wrong. **Disposition: fix now** (trivial doc correction).
11. **[edge-case, trivial] No explicit `session.rollback()` before re-raising in `save_with_evidence` on insert failure.** Matches the existing codebase-wide pattern (no other repository method rolls back explicitly either) — not a new gap introduced by this epic. **Disposition: accept as-is.**
12. **[adversarial, informational] `FollowUpOut` omits `reason`/`next_review_date` from the wire schema.** Not a defect — no UI captures these fields in Epic 4, exactly as scoped. Noted only as a forward-looking awareness item for whichever future epic adds a form for them. **Disposition: no action.**
