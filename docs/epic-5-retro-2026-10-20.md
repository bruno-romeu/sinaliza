## Findings

### Aggregate views

**Architecture delta — clean.** `app/ml/` stayed import-isolated from `presentation/` across all 4 stories (confirmed by direct grep: no `presentation/` module imports anything from `app.ml`, and no `app.ml` module imports `presentation/`). No new cross-cutting dependency or layering violation introduced by the epic.

**Duplication map — one duplication introduced, then fixed two stories later; one new duplication left in a latent, asymmetric state.**
- Story 5.2's own review flagged `PredictionRepository.fetch_scoring_rows()` duplicating `TrainingRepository`'s attendance/grade/assignment/observation aggregation SQL almost verbatim, and explicitly **deferred** it (medium severity) rather than fixing it then. Story 5.3 independently extracted `feature_aggregation.fetch_feature_rows()` as the shared helper all three repositories (`TrainingRepository`, `PredictionRepository`, `EvaluationRepository`) now call — closing 5.2's own deferred item as a side effect of 5.3's unrelated primary goal. Confirmed: `backend/app/ml/feature_aggregation.py` is the single aggregation implementation; all three repositories delegate to it (verified by direct read, cross-story review agent independently confirmed the same).
- **New, still-open duplication (cross-story boundary finding, not caught by any single story's own review):** Story 5.2 invented a `FEATURE_COLUMNS` drift guard in `prediction_repository.py:56-71` (`if tuple(FEATURE_COLUMNS) != (...): raise RuntimeError(...)`) specifically because `predict.py` hardcodes its feature-vector field order as a Python list literal rather than iterating `FEATURE_COLUMNS`. That same hardcoded-list pattern was then copied into `train.py` (Story 5.1, predates the guard) and `evaluate.py`/`evaluation_repository.py` (Story 5.3) — but the guard itself was never propagated to either. Today all three lists agree with `FEATURE_COLUMNS`, so nothing is broken yet. But if `feature_aggregation.FEATURE_COLUMNS` — "the single definition every other module imports from," per its own docstring — is ever reordered, `predict.py` fails loudly at import time while `train.py` and `evaluate.py` would silently fit/score with misaligned columns: a corrupted model or a confidently-printed-but-wrong evaluation report, with no test or runtime check to catch it. This is a genuine cross-story gap: the drift-protection pattern was invented mid-epic and never swept backward or forward. **Routed to fix-now** (see Action items).

**God-class / size growth — none.** Ranked by net churn (via `git_evidence.py`'s `files`): the largest non-test file added is `evaluate.py` at 255 lines (new file), followed by `predict.py` at 167 and `train.py` at 138 — all new, single-purpose CLI modules, none approaching a size where "did this grow into something unreviewable" is a real question. No pre-existing file grew unexpectedly large across the epic.

**Pattern divergence — one real instance, already found and fixed in this epic's own code-review passes.** `sqlalchemy_trajectory_change_repository.py`'s new `filter_as_of` call (Story 5.4) initially compared a `timestamptz` column directly to `as_of()`'s plain `date`, diverging from the established codebase pattern (`sqlalchemy_pedagogical_observation_repository.py` casts to `Date` first for the same situation). Caught and fixed during this epic's own Story 5.4 code-review pass (commit `3c4abf9`) — recorded here because it is exactly the class of defect this retrospective exists to surface, even though it was already resolved before reaching this document.

**Spec-to-implementation reconciliation — compliant.** Checked each of `epic-5-context.md`'s declared requirements against the as-built code:
- Score/prediction never in a product endpoint or schema: confirmed, `MLPrediction`/`MLPredictionModel` are never read by any `presentation/` or web-path repository (grepped).
- `dataset_split` enforced structurally, never per-endpoint convention: confirmed — `TrainingRepository` reads only `TRAIN`, `PredictionRepository`/`EvaluationRepository` read only `EVAL_DEMO`, enforced at the query level in each repository, not by caller discipline.
- `as_of()` truncation applies only to the live-serving path, never to `ml/evaluate`: confirmed asymmetric by design and by code — `EvaluationRepository`/`PredictionRepository`/`feature_aggregation.py` never call `filter_as_of`; the live Home/Trajectory path does (now including Story 5.4's fix). The epic's own context doc calls this "a deliberate, explicit application-layer difference, not something to fix toward consistency," and the code honors that.
- Evaluation metrics framing: confirmed the "ability to recognize simulated patterns in the synthetic dataset" disclaimer is printed verbatim on every `evaluate.py` report.
- `MLModelVersion`/`MLPrediction` live on dedicated tables, `synthetic_profile`/`dataset_split` stay off the product `Student` dataclass: confirmed by direct read of `backend/app/domain/student.py` and `backend/app/infrastructure/db/models.py`.

No requirement was found silently dropped, and no unspecified product-facing behavior was found added.

## Action items

1. **[fix-now]** Close the `FEATURE_COLUMNS` drift-protection gap: either add the same `if tuple(FEATURE_COLUMNS) != (...): raise RuntimeError(...)` guard (currently only in `backend/app/ml/prediction_repository.py:56-71`) to `backend/app/ml/train.py` and `backend/app/ml/evaluation_repository.py`/`backend/app/ml/evaluate.py`, or — the cleaner fix — change all three CLIs (`train.py`, `predict.py`, `evaluate.py`) to build their feature vectors by iterating `FEATURE_COLUMNS` directly instead of a hardcoded field-literal list, removing the need for a guard anywhere. Owner: dev. Evidence: cross-story boundary review (this retro), independently re-verified by direct grep against all three files.
2. **[defer, already logged]** `SqlAlchemyTrajectoryChangeRepository.get_by_id` (used by `GET /follow-ups/{id}`, `POST /follow-ups`) has no `as_of()` filter — same leak class Story 5.4 just fixed for `list_recent`, one method away in the same file. Already recorded in `docs/deferred-work.md` under "Deferred from: code review of story-5.4 (2026-10-20)" during this epic's own Story 5.4 review. No new action needed beyond what's already filed; restated here for epic-level visibility.
3. **[process lesson, escalate]** `epic-3-retro-item-3` (merge-before-done gate) had a live near-miss during this epic (see Previous-retro follow-through).
