See Finding F1.

## Findings

### F1 — [process / blocking] Epic marked `done` while three of its four stories' final, reviewed code is stranded on unmerged local branches

Sourced via `git merge-base --is-ancestor`, `git log --oneline <ref>`, and `git branch --contains <sha>`:

- **Story 3.4 is entirely absent from `master` and from the branch this retro ran on.** Its feature commit (`86589cc`, "feat: add student trajectory detail page...") and its code-review fix commit (`4df6fa8`, "fix: anchor current-period trajectory series point on real clock") exist only on local branch `feature/3-4-trajetoria-do-estudante-grafico-evidencias-fator-preocupante`. `git merge-base --is-ancestor 86589cc HEAD` → `NO`; `git merge-base --is-ancestor 86589cc origin/master` → not reachable either. `docs/sprint-status.yaml`'s own commit `02d104c` ("chore: mark Story 3.4 done after code-review follow-up fix") states the fix landed "in the sinaliza-wt-build-3-4 worktree (commit 4df6fa8)" but that worktree's branch was never merged back — `02d104c` only edits `sprint-status.yaml`, it carries no code. Right now, checking out `master` or this retro's own branch gives a Home page whose student rows link to a page that does not have the real Story 3.4 implementation.
- **Story 3.3's code-review fix is not on `master` either.** `origin/master`'s merge of PR #13 (`8f38e5c`) points directly at `2b91cdd` (the original "feat: add Home page" commit) — it was merged *before* the review-fix commit (`23db6b2`, "fix: address Story 3.3 code review findings (search cap, trim, timezone, tests)") existed. `23db6b2` was then committed only to the local checkout of this already-merged branch and never pushed/re-PR'd. Concretely, `master` today ships `GET /home/search` **without** the 20-result cap, without query trimming, and `Home.tsx` still has the UTC/local-timezone date-display bug the review found (a change detected "today" can render as yesterday's date for a Brazil-based browser) — all three were reviewed, fixed, and believed shipped, but are not live.
- **Story 3.2's code-review fix (`631575a`) is also stranded**, on `feature/3-2-deteccao-de-mudanca-relevante-por-convergencia-de-sinais`, unreachable from `master` or from this branch. Lower severity (docs/tests-only — see commit message), but the same pattern.
- **This branch itself (`feature/3-3-pagina-inicial-com-mudancas-recentes`) is 4 commits ahead of its own `origin` remote and was never pushed or re-merged** (`git rev-list --left-right --count HEAD...origin/feature/3-3-...` → `4 0`). Those 4 commits are exactly the ones that mark 3.2, 3.3's fix, 3.4, and the epic itself "done."

Net effect: **`sprint-status.yaml`'s "done" status for 3.2, 3.3, 3.4, and epic-3 does not correspond to what is reachable on `master`.** A fresh `git clone` + checkout of `master` today gets Stories 3.1–3.3's first-pass code only (no post-review fixes, no Story 3.4 at all). This matches a known pattern from this user's own notes on worktree-per-story builds: the worktree branch gets reviewed and status-stamped, but nothing in the recorded flow actually runs the merge back into the integration branch.

**Disposition:** fix-now, blocking. This is why the epic verdict below is **rejected** rather than accepted-with-open-items — the gap is in delivery, not in a deferred nice-to-have.

## Acceptance verdict

**Rejected** (profiled criteria — the epic spec does not declare a formal acceptance-criteria section separate from its per-story ACs, so the verdict is profiled from `docs/epic-3-context.md`'s Requirements & Constraints plus the four stories' own Tasks & Acceptance sections).

The profiled criteria (convergence-based detection, Home list of recent changes, trajectory detail view with evidence, accessibility floor, no ranking/score language) are substantively **met in the code that was written** — per-story review logs show no unresolved high/medium finding anywhere, and the architecture's explicit constraints (immutable `TrajectoryChange`, closed-enum types, own-history-only habitual range, no ranking UI) are correctly implemented everywhere checked.

The verdict is nonetheless **rejected** because of F1: the epic's own tracking (`sprint-status.yaml`, `done` since commit `4033353`) asserts completion that is not reachable from `master` or from the branch that was retro'd. Story 3.4 — one of the epic's four stories — has **zero presence** on `master`; Stories 3.2 and 3.3 are live on `master` only in their pre-review-fix form, including a known-and-supposedly-fixed unbounded search endpoint. Per this workflow's rubric, "a blocking finding stands unresolved" forces rejected regardless of `pending_stories` being empty — the emptiness of `pending_stories` here is itself misleading, since it reflects status-file edits made on a branch, not deliverable state on the integration branch. No human override was applied; per rule 2 of the acceptance rubric, an epic that fails its criteria with no explicit human override is recorded as rejected rather than silently accepted.

This verdict should flip to **accepted** (or accepted-with-open-items, if item 2's defects are deliberately left open a cycle) as soon as action item 1 lands and is verified on `master`.
